# 手动挡（单步推进）+ 阶段能力单一真源 设计

> 日期：2026-07-30
> 状态：**待定稿**（brainstorming 决策已定，待用户确认后转实现计划）
> 背景：一个停在「方案」阶段的历史工作项无法再被触发。排查发现这不是历史数据的偶发，而是驱动层把两种性质完全不同的"停"混成同一个静默返回；同时发现视图层手抄了一份"平台已实现阶段"的清单并已漂移。本设计引入**手动挡**作为一等节奏概念，并把阶段能力收敛为单一真源。
> 架构基准：docs/architecture/2026-07-15-strategic-direction-and-domain-model.md
> 前序：docs/superpowers/specs/2026-07-27-llm-triage-autonomy-switch-design.md（自主开关 / CONTEXT_GATE 框架）、docs/superpowers/specs/2026-07-29-design-port-real-adapter-design.md（上一次驱动边界扩容，正是本问题的触发源）

## 0. 已确认决策（brainstorming）

1. **一等手动挡**，而非"仅兜底恢复"或"启动即自愈"。任何可推进阶段都能被人单步推进；搁浅的历史工作项因此**天然可恢复**，不需要专用恢复通道。
2. **泛化现有开关，不新增旋钮**。`WorkItem.autonomy_enabled` 从"只管上下文后决策"升级为真正的节奏总开关：开 = 自动挡，关 = 手动挡。
3. **手动挡下"只读收集段"仍连续自动跑**（录入 / 分诊 / 上下文），保留"建完工作项即可看到分诊与简报"的体验；人工控制点落在"要花大钱、要动东西"之前。
4. **人的每一次点击 = 推进一个阶段**。CONTEXT_GATE 的「继续」在手动挡下即视为"授权走这一步"，直接执行 DESIGN 后停住，避免为同一个意图点两下。
5. **手动挡不绕过风险门禁**。单步推进若产出挂起，照常进 `WAIT_HUMAN` 并显示三键面板。节奏控制与审批是两件事。
6. **`WAIT_HUMAN` 与 `GatePoint` 语义完全不动**（铁律 5 不受影响）。手动挡的"停"不是门禁，不获得拒绝语义。

## 1. 非目标

- 真实 Review / Execution / Verification / Delivery 适配器（仍为 `UnavailableStage` 桩）。
- 并发双击的后端强防护（乐观锁 / 领取锁）。本次靠前端按钮 disable + 查询失效覆盖日常；彻底解决属 ROADMAP 横向关切面「并发与调度」，不在此夹带。见第 8 节。
- 阶段级细粒度配置（"哪些阶段要我点"交给配置面）。当前单用户、下游多为桩，属过度工程。
- 复用 `AutonomyDial` 做逐阶段自动/人工决策（切片 4 信任梯度的事）。

## 2. 问题诊断

三个互相纠缠的事实，其中第 3 条是**当前已在线上的 bug**。

### 2.1 驱动层把两种"停"混为一谈

`webapp/service.py` 的有界驱动循环里：

```python
if not work_item.is_runnable() or work_item.state not in run_states:
    return
```

- 前半句 = 终态或 `WAIT_HUMAN` —— **合法地停**。`WAIT_HUMAN` 是一等状态：带 `pending_gate`、有恢复入口、有前端面板。
- 后半句 = "平台还做不了这个阶段" —— **搁浅**。它不是状态，只是*触发的缺失*：没有恢复入口、没有 UI、没有任何痕迹。

而界面上二者难以区分：搁浅项的当前阶段照常显示为进行中（橙点），看着在跑，实际永不再动。

### 2.2 每次扩容都会制造一批搁浅工作项

驱动边界每扩一次（上一次从 CONTEXT 扩到 DESIGN，下一个是 REVIEW），当时停在新增阶段外沿的工作项就永久失联。这是机制性的必然，不是偶发。

### 2.3 视图层手抄了阶段能力清单且已漂移

`webapp/views.py` 里维护了一份"未实现阶段"集合，与驱动用的那份是同一个事实的第二份手抄。DESIGN 已实现并进入驱动集合，但仍留在"未实现"清单里。实测（停在上下文阶段的新工作项）：

```
方案  status=blocked（待建设）   而驱动集合里有它 = True
```

即**已交付的方案功能，UI 上仍写着「待建设」**。与同期修掉的注释漂移同源：一个事实抄了两份。

## 3. 单一真源：阶段能力集合

把"这个组合根下平台能执行哪些阶段"收敛为**一个**值，三个消费者共用：

```
IMPLEMENTED_STAGES  ← 唯一真源
   ├─ 驱动：自动挡连续推进的边界
   ├─ 投影：哪些阶段标「待建设」
   └─ 按钮：下一阶段在其中 → 「推进」可点
```

- `service.py` 的 `RUN` **改名**为 `IMPLEMENTED_STAGES`。名字应说明它*是什么*，而不是某一个消费者拿它*干什么*——它现在有三个消费者。生产值 = 录入 / 分诊 / 上下文 / 方案。
- `views.py` 的"未实现阶段"集合**删除**。`stage_views` / `view_detail` 增一个参数接收阶段能力集合，并**从 `service.py` 导入同一个常量**作为默认值——只有一处定义，不是各自维护一份默认。演示组合根通过路由层显式注入自己的集合。
- 演示组合根照旧注入全阶段集合，顺带修掉演示 UI 里方案及之后也被标「待建设」的问题。

**效果**：驱动边界扩容的那一刻，所有停在新增阶段的老工作项按钮自动变亮，无需任何补偿动作——2.2 的复发机制消失。

## 4. 停因分类（纯函数）

新增 application/webapp 层的纯函数与枚举（**不进 `domain/`**，铁律 1）：

```python
COLLECT_STAGES = {INTAKE, TRIAGE, CONTEXT}   # 只读收集段：手动挡下也连续跑

class DriveStop(Enum):
    TERMINAL        = auto()   # DONE / FAILED
    WAIT_HUMAN      = auto()   # 门禁挂起，须走 /decide
    NOT_IMPLEMENTED = auto()   # 平台尚无该阶段实现
    MANUAL_HOLD     = auto()   # 手动挡，等人点

def classify(wi, implemented) -> DriveStop | None:
    if wi.state in (DONE, FAILED):   return DriveStop.TERMINAL
    if wi.state is WAIT_HUMAN:       return DriveStop.WAIT_HUMAN
    if wi.state not in implemented:  return DriveStop.NOT_IMPLEMENTED
    if not wi.autonomy_enabled and wi.state not in COLLECT_STAGES:
                                     return DriveStop.MANUAL_HOLD
    return None                      # 可继续自动推进
```

**停因是推导而非持久化的。** 推导输入（`state`、`autonomy_enabled`、阶段能力集合）分别是持久化字段与组合根常量，函数纯粹，进程重启后结果一致。这是本方案相对"复用 `WAIT_HUMAN` + 新增通用门"方案的取舍点：换来领域状态机零改动与历史数据零迁移。

## 5. 两个驱动入口

`MANUAL_HOLD` 只挡**自动**驱动，不挡人明确要求的那一步——否则手动挡下永远动不了。

| 入口 | 行为 | 调用方 |
|------|------|--------|
| 自动驱动 | 循环推进，`classify` 一返回停因即停 | 建工作项 |
| 单步推进 | **只走一步**，无视 `MANUAL_HOLD`（人已授权）；仍拒绝 TERMINAL / WAIT_HUMAN / NOT_IMPLEMENTED | 「推进」按钮 |

`decide_workitem("proceed")` 按模式分流：手动挡走单步，自动挡走自动驱动。

单步推进直接复用**已存在但从未接线**的 `advance_work_item`（`application/entrypoints.py`），不新增领域入口。

### 5.1 场景走查

```
建项(手动挡)   录入→分诊→上下文 连续跑 → CONTEXT_GATE 挂起  → 三键面板
点「继续」     单步: 跑 方案 → 停在 评审                     → 「推进」按钮
点「推进」     单步: 跑 评审(落地后) → 停在 开发               → 「推进」按钮
建项(自动挡)   连续跑到能力边界或门禁挂起                      → 行为不变
```

搁浅的历史工作项（停在方案、自动挡、方案已进能力集合）：`classify` 不返回任何停因（即"可推进"）→ 按钮亮，点一下即跑。**零迁移。**

### 5.2 收集段进行中也会显示「推进」按钮——这是有意的

手动挡下，工作项短暂停留在收集段（如分诊）时，`classify` 判定"可推进"，于是「推进」按钮会出现，而此时后台线程可能正在推进它。看似矛盾，但这是刻意选择：

- 若改为"收集段一律不给按钮"，那么**驱动进程在收集途中崩溃/被杀的工作项将永久搁浅、没有任何恢复入口**——正是本设计要消灭的那个缺陷形态。
- 保留按钮意味着"可推进"始终等价于"有入口"，不存在无 affordance 的可推进态。这条不变式比避免短暂的按钮闪现更值钱。

代价是此窗口内双击可能推进两个阶段，归入第 8 节声明的并发非目标。

## 6. 投影与 API

`view_detail` 新增单一投影字段 `next_action`，前端不重复判断逻辑：

| `next_action` | 触发条件 | 界面 |
|---------------|----------|------|
| `advance` | `classify ∈ {None, MANUAL_HOLD}` | 主按钮「推进下一步 →」+ 下一阶段名 |
| `decide` | WAIT_HUMAN | 现有三键面板（不动） |
| `blocked` | NOT_IMPLEMENTED | 灰按钮 + 「<阶段> 尚未建设」 |
| `none` | TERMINAL | 无操作 |

新增端点：

```
POST /api/workitems/{id}/advance   → 单步推进，返回更新后的 detail
                                     非法态（终态/待门禁/未实现）返回 409
```

## 7. 前端

- 工作项详情页新增「推进」区，按 `next_action` 渲染四态。
- 建工作项复选框文案由"启用 AI 自主"改为节奏语义（自动挡 / 手动挡），**默认仍为手动挡**（与现有默认一致）。
- 按钮点击后立即 disable，成功后失效详情查询。

## 8. 错误处理与不变式

- 单步推进遇非法态：服务层返回明确失败，路由映射 409，**不**静默无操作（这正是原缺陷的形态）。
- 阶段处理器抛错：沿用既有 `StageOutcome` / 重试 / 回退路径，收敛到 FAILED（铁律 7），本设计不新增失败路径。
- 并发双击：两次快速点击可能推进两个阶段。前端 disable 覆盖日常；后端强防护需乐观锁，属 ROADMAP「并发与调度」，本次显式不做并已在第 1 节列为非目标。
- **行为变更（有意）**：`autonomy_enabled` 为关的既有工作项，行为从"过了 CONTEXT_GATE 便连续跑"变为"每步等人点"。这是决策 2 的直接后果，须写入 CHANGELOG。

## 9. 测试（TDD，先红后绿）

1. `classify` 组合表单测：状态 × 模式 × 能力集合，覆盖四种停因与"可继续"。
2. 驱动：手动挡建项停在 CONTEXT_GATE；`proceed` 后只推进一个阶段；自动挡连续跑到能力边界；搁浅项可被单步推进。
3. 投影：`next_action` 四态；**回归断言方案阶段不再被标「待建设」**（即 2.3 那个 bug）。
4. **防漂移守卫**：沿用既有安全守卫的做法（`tests/webapp/test_demo_app.py` 里以 `isinstance(..., UnavailableStage)` 逐端口断言），对生产组合根断言——阶段能力集合里的每个阶段，其对应端口**不是** `UnavailableStage`；集合外的每个阶段，其端口**是** `UnavailableStage`。下次谁加了真适配器却忘了更新集合，测试直接失败。本设计中最有价值的一条测试。
   *坦白其局限*：该断言需要一份"阶段 → 端口"映射，它本身也是手工维护的。但它住在测试里，漂移的后果是**测试大声失败**而非线上静默错标——这正是把隐性事实转成显式断言的意义。
5. 路由：单步推进成功 / 409 两路。
6. 前端 vitest：按 `next_action` 渲染四态；按钮点击触发变更。
